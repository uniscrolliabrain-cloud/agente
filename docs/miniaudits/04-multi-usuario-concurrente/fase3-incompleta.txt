# 08 — Campaña 2 / Fase 3 — Delegación controlada (G3)

------------------------------------------------------------------------------------------------

## Veredicto: la Fase 3 necesita correcciones antes de ejecutarse con Cline

La arquitectura tiene una buena dirección: unificar tareas, objetivos, monitores, aprobaciones y SOP bajo una interfaz de asignación, sin duplicar su persistencia; separar al actor que solicita del que ejecuta; y construir `Flow` desde `AgentPersona`, que es donde realmente existen `reportsTo` y `peers`.

Pero no daría este documento por listo para ejecución todavía. Hay contradicciones en el contrato de delegación, riesgos de autorización heredados de la Fase 2 y una implementación de los adapters que puede perder datos. Además, las cifras de patchsets no cuadran.

Mi recomendación es corregir primero los puntos siguientes y después pasarle a Cline el documento revisado, no los 26 patchsets de golpe.

## 1. Bloqueantes: delegación y permisos

### 1.1. «Hereda los permisos del asignador» no está definido de forma segura

El documento afirma que el agente ejecutor hereda los permisos del asignador, limitados al ámbito de la tarea. Sin embargo, eso no especifica cómo se calcula la intersección de permisos.

La regla correcta debería ser:

\\[ P\_{\text{efectivos}} = P\_{\text{asignador}} \cap P\_{\text{ejecutor}} \cap P\_{\text{tarea}} \cap P\_{\text{tenant}} \\]

Es decir, el agente no debe adquirir permisos que el asignador no tenga, ni saltarse las restricciones propias del ejecutor, ni salir del ámbito de la tarea o del tenant.

Corrección para el documento: exigir que cada acción delegada compruebe al menos:

- Identidad del solicitante y del ejecutor.
- Tenant y recurso reales sobre los que se opera.
- Que la asignación autoriza esa acción concreta.
- Que el actor no puede autoasignarse permisos superiores.
- Que aprobar, rechazar, reasignar y escalar son permisos distintos.
- Que el ejecutor no puede aprobar su propia acción cuando se requiere separación de funciones.

Esto depende directamente de que el PDP de Fase 2 sea realmente fail-closed. En la revisión anterior detecté un posible bypass en el ejemplo de `PolicyDecisionPoint`: se invocaba `PolicyEngine.can` con un rol artificial `{id: roleId}`, sin sus permisos reales. Si esa implementación sigue en el repositorio, Fase 3 no debe darse por segura hasta corregirla.

### 1.2. `assignedBy` y `assignedTo` no pueden confundirse con `owner`

En el documento se dice que, si no hay asignación explícita, se usa el `owner` actual como asignador y asignado por defecto.

Eso mezcla conceptos diferentes:

- `owner`: propietario o ámbito de almacenamiento.
- `assignedBy`: actor que delega.
- `assignedTo`: actor que recibe la tarea.

No tienen por qué compartir el mismo identificador. El `owner` puede representar una cuenta o partición, mientras que el actor puede ser una persona o un agente.

Corrección: resolver el actor autenticado desde el contexto de la petición. Mantener `owner` para el ámbito de almacenamiento y utilizar `assignedBy` y `assignedTo` para las identidades de delegación. Si no existe un actor autenticado o no se puede resolver el destinatario, la operación debe fallar, no inventar una identidad a partir de `owner`.

### 1.3. Las rutas de asignaciones deben autorizar el recurso real

Añadir `withRead`, `withWrite` y PDP a las rutas no basta por sí solo. Cada handler debe cargar el recurso original, verificar su tenant y su identidad, autorizar la transición solicitada y solo entonces escribirlo.

Por ejemplo, en `POST /api/assignments/:kind/:id/approve`, no debe bastar con que el usuario tenga permiso genérico para aprobar: hay que comprobar que puede aprobar esa propuesta concreta, que está en un estado aprobable y que no se está aprobando a sí mismo cuando eso esté prohibido.

También hay que evitar que el cliente pueda enviar `tenantId`, `assignedBy`, `status` o `kind` para saltarse las restricciones. Esos valores deben derivarse del contexto autenticado o validarse contra el registro original.

## 2. Bloqueantes: el modelo `Assignment` y los adapters

### 2.1. `Assignment` no es todavía un contrato común completo

El modelo base declara:

```
assignedTo: z.string().min(1).max(200),
status: assignmentStatusSchema,
plan: assignmentPlanSchema.optional(),
evidence: z.array(assignmentEvidenceSchema).max(50).default([]),
outcome: assignmentOutcomeSchema.optional(),
```

Pero cada registro original tiene una estructura diferente. Por ejemplo, `AgentTask` utiliza `TaskStep[]`, `Evidence[]` y un `Outcome` propio. El schema específico de tareas reemplaza esos tipos con `z.any()`.

Eso elimina parte de la validación que el modelo común pretende aportar. También hace posible aceptar objetos que no cumplen los contratos reales del dominio.

Corrección: no usar `z.any()` para `plan`, `evidence` y `outcome`. Los adapters deben convertir explícitamente los tipos originales al formato común y validarlos. Si los tipos no son compatibles, hay que definir una transformación concreta o conservar el dato original en una estructura tipada.

### 2.2. `fromAssignment()` no puede reconstruir datos que no existen en `Assignment`

El documento permite guardar campos adicionales en `metadata` cuando un adapter los necesita, pero `assignmentSchema` no declara ese campo. Además, los adapters prometen traducción de ida y vuelta, mientras que el modelo común omite atributos específicos de los registros originales.

Eso puede provocar pérdida de datos al convertir un registro a `Assignment` y después reconstruirlo.

Corrección: antes de escribir los cinco adapters, definir un contrato claro:

- `toAssignment(record)` produce una vista normalizada, sin modificar el registro.
- `applyAssignment(record, changes)` aplica únicamente los campos autorizados al registro original.
- Los campos específicos que no forman parte de `Assignment` se conservan en el registro original, no se reconstruyen a partir de una vista incompleta.
- Si se necesita `metadata`, debe estar definido y validado en el schema.
- La prueba de ida y vuelta debe comprobar que no se pierden datos ni se modifican campos ajenos a la operación.

No basta con decir que el adapter es idempotente: hay que especificar qué significa esa propiedad para cada tipo de registro.

### 2.3. La interfaz común exige `assignedTo`, pero el propio plan contempla registros sin destinatario

El documento dice que, cuando no se proporciona destinatario, se asigna al propietario actual. Esa regla es cuestionable por la distinción entre propietario y actor, y puede ser incompatible con registros existentes que todavía no tengan `assignedTo`.

Corrección: decidir expresamente si toda `Assignment` debe tener destinatario o si una asignación puede estar sin asignar. Si se admite una bandeja de pendientes, el modelo y sus rutas deben representarla explícitamente; no hay que inventar un destinatario para satisfacer el schema.

## 3. `Flow`: buena decisión de origen, pero falta resolver la identidad

Construir `Flow` desde `AgentPersona.reportsTo` y `peers` es coherente con los datos disponibles. No lo construiría desde `AgentRole`.

Sin embargo, `AgentPersona` utiliza identificadores de persona de hasta 80 caracteres y los relaciona mediante strings. El nuevo `FlowRelation` utiliza `actorId`, con un límite de 200 caracteres, y un `kind` que distingue entre humanos y agentes.

El documento no define cómo se traduce un `persona.id` a un actor real, ni cómo se resuelve el tenant de las relaciones.

Corrección:

- Resolver cada relación contra un actor existente en el mismo tenant.
- No asumir que `persona.id === actor.id`.
- Rechazar o señalar referencias inexistentes, relaciones cruzadas entre tenants y relaciones inválidas.
- Evitar que `peers` se convierta en un permiso de delegación: ser par no implica poder asignar, aprobar o escalar.
- Definir si una relación `reportsTo` apunta a un agente, una persona o una persona organizacional representada por otro tipo de registro.

La construcción de `Flow` no debería conceder permisos por sí misma.

| `SOP`                   | `POST /:id/run` asigna el SOP al actor que ejecuta.                                                                         | Separar el propietario del SOP, el solicitante de la ejecución y el actor que la ejecuta.                        |

Hay otro punto importante: `assignmentStatusSchema` introduce estados como `waiting_approval`, `scheduled`, `paused` y `cancelled`. Los adapters deben mapearlos a estados válidos del registro original. Si un tipo no admite alguno de esos estados, la conversión debe ser explícita y no una asignación arbitraria.

## 5. El bloqueo de tests no encaja con los criterios de aceptación

La Fase 3 prohíbe crear cualquier `tests/*.test.ts` hasta F7, pero después exige probar:

- Autorización correcta e incorrecta.
- Aislamiento entre tenants.
- Adaptadores e idempotencia.
- Delegación sin elevación de permisos.
- Rutas que responden `200` o `403`.
- Integración con `AgentService`, `ActionService` y `sopRoutes`.

Un typecheck verde no demuestra ninguna de esas propiedades. Y ejecutar `pnpm test` sobre los tests antiguos tampoco garantiza que se hayan probado los nuevos comportamientos.

Mi recomendación es conservar congelados los tests ajenos a la campaña, pero permitir pruebas específicas de Fase 3 en un directorio autorizado, o ejecutar pruebas temporales reproducibles que no se incorporen al repositorio. Si no se permite ninguna de las dos opciones, el cierre de Fase 3 debe quedar condicionado: no puede declararse verificada la delegación segura.

## 6. Cómo ejecutaría la fase

No cambiaría el objetivo de producto. Cambiaría el orden para reducir el riesgo y facilitar el diagnóstico.

## 1

Contrato de dominio

`Assignment`, `Flow`, schemas específicos y reglas de conversión. Primero definir estados, campos obligatorios y preservación de los datos originales.

## 2

Adapters y registry

Implementar los cinco adapters y comprobar que leen y actualizan correctamente cada tipo de registro, sin persistir una entidad `Assignment` duplicada.

## 3

Servicio de delegación

`assign`, `accept`, `reject`, `approve`, `escalate`, `reassign` y `complete`, con autorización por recurso y transición.

## 4

Integración

Rutas, `AgentService`, `ActionService`, SOP y personas. Revisar cada integración por separado antes de cablear `app.ts`.

## 5

Verificación y cierre

Typecheck, pruebas específicas, revisión de permisos y `git diff`. Commit explícito solo después de comprobar qué cambios pasan y cuáles no.

Mantendría la restricción de no tocar `worker.ts`, `conversation.ts`, el kernel fuera del alcance autorizado y los componentes reservados a F4–F7. Si un requisito de delegación no puede implementarse sin tocar uno de esos componentes, se documenta el bloqueo; no se amplía el alcance silenciosamente.

## Conclusión

La Fase 3 es viable, pero el documento todavía no está listo para ejecutarse tal cual. Los cambios más importantes antes de entregárselo a Cline son:

1. Definir la intersección real de permisos heredados y comprobar el PDP de Fase 2.
2. Separar inequívocamente `owner`, `assignedBy` y `assignedTo`.
3. Corregir los schemas permisivos y garantizar que los adapters no pierdan datos.
4. Definir las reglas de identidad y tenant de `Flow`.
5. Resolver la contradicción entre la prohibición de tests y las pruebas obligatorias.
6. Corregir el conteo y tener los 26 patchsets completos antes de empezar.

La idea central —una interfaz común de asignaciones sobre los registros existentes— sigue siendo buena. Lo que conviene evitar es construir una API de delegación aparentemente completa que, por debajo, tenga permisos ambiguos, adaptadores con pérdida de datos o transiciones que se puedan saltar.

### Patchset F3.1 — `packages/domain/src/assignment.ts`

**Fichero:** `packages/domain/src/assignment.ts` (CREATE)
**Marca:** `ASSIGNMENT_MODEL_V1`

**Contenido:**

```typescript
// ASSIGNMENT_MODEL_V1 — interfaz de lectura unificada de asignación.
// AgentTask (task), Goal (goal), Monitor (monitor), ActionProposal (approval),
// SOP (sop) son implementaciones. NO se persiste como entidad propia.
// Se computa on-the-fly desde el record original usando el adapter.
import { z } from "zod";

export const assignmentKindSchema = z.enum(["task", "goal", "monitor", "approval", "sop"]);

export const assignmentStatusSchema = z.enum([
  "queued", "running", "waiting_input", "waiting_approval",
  "scheduled", "paused", "succeeded", "failed", "cancelled",
]);

export const assignmentPlanStepSchema = z.object({
  id: z.string().min(1).max(200),
  title: z.string().min(1).max(300),
  status: z.enum(["pending", "running", "succeeded", "failed", "waiting"]).default("pending"),
  detail: z.string().max(2000).optional(),
});

export const assignmentPlanSchema = z.array(assignmentPlanStepSchema).max(200);

export const assignmentEvidenceSchema = z.object({
  id: z.string().min(1).max(200),
  kind: z.enum(["mail", "file", "web", "user"]),
  title: z.string().min(1).max(300),
  excerpt: z.string().max(4000),
  url: z.string().max(4096).optional(),
});

export const assignmentOutcomeSchema = z.object({
  status: z.enum(["succeeded", "failed", "partial", "rejected"]),
  summary: z.string().max(4000),
  evidence: z.array(assignmentEvidenceSchema).max(50).default([]),
  completedAt: z.string(),
});

export const assignmentSchema = z.object({
  id: z.string().min(1).max(200),
  tenantId: z.string().min(1).max(100),
  kind: assignmentKindSchema,
  assignedTo: z.string().min(1).max(200),
  assignedBy: z.string().min(1).max(200).optional(),
  status: assignmentStatusSchema,
  plan: assignmentPlanSchema.optional(),
  evidence: z.array(assignmentEvidenceSchema).max(50).default([]),
  outcome: assignmentOutcomeSchema.optional(),
  createdAt: z.string(),
  updatedAt: z.string(),
});

export type AssignmentKind = z.infer<typeof assignmentKindSchema>;
export type AssignmentStatus = z.infer<typeof assignmentStatusSchema>;
export type AssignmentPlan = z.infer<typeof assignmentPlanSchema>;
export type AssignmentEvidence = z.infer<typeof assignmentEvidenceSchema>;
export type AssignmentOutcome = z.infer<typeof assignmentOutcomeSchema>;
```
