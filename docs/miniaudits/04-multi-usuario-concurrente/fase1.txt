    this.validateAccessKey(accessKey);
    const token = randomBytes(32).toString("base64url");
    await this.db.put("system", "sessions", {
      id: digest(token).toString("hex"),
      owner: ownerId,
      expiresAt: Date.now() + (Number(process.env.SESSION_TTL_MS ?? "604800000") || 604800000),
    });
    return { token, mode: this.config.mode, ownerId };

  async owner(authorization?: string) {

    const session = await this.db.get<{ owner: string; expiresAt: number }>(
      "system",
      "sessions",
      digest(authorization.slice(7)).toString("hex"),
    );
    if (!session || session.expiresAt < Date.now())
      throw new AppError("Session expired. Sign in again.", 401);
    return session.owner;
  }

## Cinco bloqueos que resolvería antes de Fase 1

1\. `AgentActor.id` debe identificar una instancia estable. `AgentRole.id` identifica un rol, no necesariamente un agente concreto. Si se usa como identidad del ejecutor, varios agentes podrían quedar confundidos en auditoría y autorización. Hay que definir de dónde sale el identificador estable de cada instancia.

2\. `authProviderId` no queda garantizado como único. Comprobar duplicados mediante `getByAuthProviderId()` antes de escribir no evita dos altas concurrentes con el mismo valor. La unicidad debe garantizarse en el almacenamiento o mediante una operación atómica equivalente.

3\. La verificación del JWT necesita un contrato completo. No basta con validar el esquema Zod de los claims: la implementación debe verificar criptográficamente la firma y comprobar `iss`, `aud`, `exp` y los demás requisitos aplicables. La selección de claves JWKS también debe gestionar rotaciones y fallos de forma segura.

4\. `PolicyEngine.can(owner = actor.id)` puede romper la autorización existente. El identificador de actor no debe sustituir automáticamente al propietario o ámbito de almacenamiento. Hay que separar identidad del actor, tenant y ámbito de datos, y comprobar cómo funciona realmente el motor actual.

5\. El fallback del worker a `owner` no equivale a atribución real. Si no existen `assignedTo` y `assignedBy`, asignar ambos a partir de `owner` puede generar una falsa impresión de trazabilidad. El fallback debe quedar identificado como compatibilidad heredada, no como identidad demostrada.

## Dos ajustes adicionales

- Caché de tenant: un TTL de 30 segundos no debe permitir que una pertenencia revocada siga autorizando operaciones. La autorización vigente debe comprobarse por separado de la caché de contexto.
- Pruebas de auditoría: distinguir explícitamente entre una denegación auditada y una lectura sensible autorizada. Son sucesos diferentes y necesitan pruebas distintas.

Mi recomendación es conservar el documento como base conceptual y resolver estos puntos antes de congelar F1. No hace falta rehacer la campaña: basta con ajustar los contratos afectados y sus pruebas.

Después sí tiene sentido continuar con el documento 07 — Fase 2, acceso seguro (G2), pero manteniendo la misma regla: Cline inspecciona el código real, adapta cada patchset a sus anclas verificadas y no declara la fase cerrada hasta demostrar las pruebas.
