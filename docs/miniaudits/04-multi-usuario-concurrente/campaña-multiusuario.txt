2.3. auth.ts — validación de access key defectuosa
typescript
if (
  this.config.mode === "live" &&
  (!accessKey ||
    !this.config.accessKey ||
    !timingSafeEqual(digest(accessKey), digest(this.config.accessKey)))
)
digest() devuelve un Buffer, y timingSafeEqual compara buffers. Pero si accessKey y config.accessKey tienen longitudes distintas, timingSafeEqual lanza excepción, no devuelve false. En live sin OPENMUSE_ACCESS_KEY configurada, config.accessKey es undefined → !config.accessKey es true → cortocircuita y lanza 401. Correcto por accidente, pero no es fail-closed robusto. Candidato a fix.

2.4. users.ts — ensureAdmin con race condition
typescript
async ensureAdmin(email, password, name = "Admin"): Promise<User | null> {
  const existing = await this.list();
  if (existing.length > 0) return null;
  return this.create({ email, name, password, role: "admin" });
}
Dos procesos concurrentes pueden pasar existing.length === 0 y crear dos admins. En app.ts se llama al arrancar, así que en un despliegue multi-proceso (Fly/Render) es un riesgo real.

2.5. orchestrator.ts — outcome.verified = false siempre
typescript
const outcome: Outcome = {
  status: execution.status === "succeeded" ? "achieved" : "failed",
  summary: `Ejecutados ${execution.steps.length} pasos`,
  evidence: [],
  metrics: [],
  verified: false,   // ← hardcoded
};
El verifier se llama después, pero el outcome que se le pasa siempre dice verified: false. Si el verifier depende de ese campo (y DeterministicVerifier lo ignora, pero LLMVerifier no sabemos), el ciclo Goal→Verify→Replan está sesgado. Además, el orchestrator no persiste el outcome en la task.

2.6. policy/engine.ts — canWithContext delega pero no valida el tenant
typescript
async canWithContext(ctx: PolicyContext, role: PolicyRoleInput): Promise<PolicyDecision> {
  return this.can(ctx.tenantId, role, ctx.resource, ctx.action);
}
can() recibe owner como primer parámetro, pero aquí se le pasa ctx.tenantId. Mezcla owner y tenantId. En multi-tenant real, un owner de tenant A puede evaluar contra el rol de tenant B. Bug de aislamiento.

2.7. actions.ts — ACTION_EDIT_V1 recalcula hash pero no valida newData
typescript
const nextHash = createHash("sha256")
  .update(JSON.stringify({ data: newData, connectionId: action.connectionId }))
  .digest("hex");
newData es Record<string, unknown> sin schema. Un usuario puede editar una propuesta email.send y meter data: { to: ["attacker@evil.com"] } sin que proposalSchema lo valide. El hash cambia, pero el contenido no se revalida contra el schema del kind. Bypass de validación de dominio.

2.8. events/bus.ts — globalSchemaRegistry registra tipos duplicados en silencio
typescript
for (const [t, s] of Object.entries(payloadSchemas)) {
  try { globalSchemaRegistry.register({ type: t as SystemEventType, version: "1.0", schema: s }); } catch { /* ya registrado */ }
}
El catch vacío oculta un tipo duplicado o un schema mal formado. Si payloadSchemas tiene un typo en una clave, el registry no lo registra y el emit posterior falla en runtime sin traza. Debe loguearse, no silenciarse.

2.9. kernel/graph/promote.ts — classifyWithTenant no se usa en promote()
El fichero importa classifyWithTenant y lo usa, pero el resultado de consolidate() no se persiste en ningún sitio (solo se devuelve en el PromotionResult). El comentario CONSOLIDATE_PERSIST_V1 dice "persiste el resultado para no recalcular", pero no hay db.put. El comentario miente. El protocolo prohíbe esto explícitamente.

2.10. tenant.ts — setMembership llama invalidateAll pero no emite evento
typescript
this.cache.set(owner, { tenantId, at: Date.now() });
this.invalidateAll();
invalidateAll() borra toda la cache, incluida la que se acaba de setear. El comentario dice "invalidar toda la caché es más seguro", pero anula el this.cache.set anterior. Si el caller confía en que tenantIdFor(owner) devuelve el nuevo tenant inmediatamente, falla: la siguiente llamada recalcula desde DB (correcto, pero lento) o desde default (si la DB no se ha actualizado aún → fail-open). Bug sutil.

2.11. middleware/request-logger.ts — logContext.enterWith en middleware
enterWith en Hono/Node cambia el contexto para el resto del request, pero si otro middleware posterior también llama enterWith con owner, se pierde el correlationId original (porque logContext.getStore() devuelve el último). El withLogContext del inicio queda enterrado. En app.ts hay exactamente ese patrón: requestLogger() → luego app.use("/api/*", ...) que hace logContext.enterWith({ ...current, owner }). El correlationId sobrevive solo si current lo incluye. Hay que verificar que current no sea undefined en ese punto.

2.12. config.ts — readConfig valida live pero no sample con DATABASE_URL
En sample, si DATABASE_URL apunta a Postgres productivo, readConfig no lo impide. HOST se valida como loopback, pero la DB no. Riesgo de escribir datos de sample en una DB real. El protocolo exige fail-closed; esto no lo es.

Lo que he discernido del revisor
El revisor senior identificó 6 bloqueos y 7 inconsistencias. Coincido en todos. Los resumo aquí porque la nueva Fase 3 los incorpora como precondiciones de seguridad y como decisiones de contrato:

Permisos heredados: P_efectivos = P_asignador ∩ P_ejecutor ∩ P_tarea ∩ P_tenant. No hay herencia unilateral.

assignedBy ≠ owner: el assigner es ctx.actor.id, no el owner del store.

Rutas de asignación: cada handler carga el recurso, verifica tenant, autoriza transición, y solo entonces escribe.

z.any() prohibido: los adapters convierten explícitamente TaskStep[], Evidence[], Outcome al tipo común, o conservan el original tipado.

Ida y vuelta: toAssignment produce vista normalizada, applyAssignment aplica solo campos autorizados, los campos específicos se conservan en el record original.

Assignment sin destinatario: si se admite bandeja de pendientes, se modela explícitamente. No se inventa assignedTo.

Flow sin identidad resuelta: persona.id no es actor.id. Hay que resolver contra un actor existente, validar tenant, rechazar cruces.

ActionService.propose sin taskId: definir comportamiento explícito, no dejar aprobaciones sin control.

SOP propietario ≠ ejecutor: separar.

escalate/reassign con body incompleto: contrato inequívoco.

AgentActor.flow: definir resolución y ciclo de vida antes de añadirlo.

Status por kind: Goal (active, paused, completed), Monitor (active, paused, stopped), ActionProposal (9 estados), SOP (active: boolean) no mapean al assignmentStatusSchema de 9 estados. Hay que definir el mapeo o cambiar el schema.

Símbolo	Significado
CREATE	El fichero no existe en el árbol; el patchset lo crea.
MODIFY	El fichero existe; el patchset lo modifica con $old/$new y Assert-MatchCount.
WIRE	El fichero existe; el patchset añade una llamada/registro (p. ej. app.route(...)) sin reescribir el cuerpo.
READ	El patchset solo lee el fichero con Select-String o Get-Content para verificar anclas. No lo modifica.
NO TOUCH	Prohibido modificarlo en esta campaña; si aparece un cambio necesario, se documenta como deuda.
Reglas de idempotencia:

Cada MODIFY/CREATE lleva una marca única AMBITO_FICHERO_V<n> en un comentario del código.

Si la marca ya existe y el checksum coincide → SKIP.

Si la marca existe y el checksum no coincide → AVISO y abortar.

Si la marca no existe → aplicar.

Reglas de tamaño:

Un subdocumento (F2-core, F2-routes, F3-core, F3-adapters) no debe superar 1,2 MB de texto. Si lo supera, se parte en -part1 / -part2.

Una IA ejecutora debe poder leer el documento completo + los ficheros READ + ejecutar los patchsets sin superar el 50 % del contexto. Si no cabe, se le pasa solo el subdocumento.
