## 2. Qué conseguimos con esta fase

- **`Policy`** (F2.1): `packages/domain/src/policy.ts` con `Policy`, `PolicyAction`, `PolicyResource`, `PolicySubject`, `PolicyCondition`, `PolicyDecision`. **Solo recursos reales** (`task`, `goal`, `monitor`, `memory`, `artifact`, `sop`, `role`, `action`, `computer`, `file`, `rag`, `audit`, `presence`, `lock`, `notification`, `thread`, `project`). **No** `employee`, `payroll`, `invoice`, `document`, `business-entity` (producto, otra campaña).
- **`FieldClassification`** (F2.2): `packages/domain/src/classification.ts` con `FieldClassification`, `ClassifiedField`, `ClassifiedRecord`.
- **`PolicyDecisionPoint`** (F2.3): `apps/server/src/engine/authz/pdp.ts`. `can(ctx, action, resource, field, target)` con fail-closed y deny-overrides. **Sin `Policy` declarativo nuevo**: el PDP traduce `AgentRole.permissions` a `Policy` en el arranque y evalúa sobre el resultado de `PolicyEngine` cuando aplica.
- **`PolicyEnforcementPoint`** (F2.4): `apps/server/src/engine/authz/pep.ts`. **Autorización en handlers, workers, acciones internas, streams, rutas alternativas**. No middleware global como única defensa.
- **`FieldFilter`** (F2.5): `apps/server/src/engine/authz/field-filter.ts`. **Aplicado en lectores, escritores, serializadores, listados, búsquedas, agregaciones**. No solo en `withRead`.
- **`withRead`** (F2.6): `apps/server/src/engine/authz/with-read.ts`. Envuelve `db.get` y `db.list`. PDP + `FieldFilter` + `AuditTrail` si el campo es `restricted`/`secret`.
- **`withWrite`** (F2.7): `apps/server/src/engine/authz/with-write.ts`. Envuelve `db.put` y `db.compareAndSwap`. PDP + CAS (sin `version` todavía, eso es F4) + `AuditTrail`. **No** aplica `expectedVersion` (F4). **No** aplica diff (F4).
- **`policies.ts`** (F2.8): `apps/server/src/engine/authz/policies.ts`. Traduce `AgentRole.permissions`, `AgentRole.allowedTools` a `Policy` y añade políticas por defecto. Owner no es root (I15): si no hay política para `secret`, no lo ve.
- **Clasificación aplicada a campos reales** (F2.9): `User.email: internal`, `User.name: internal`, `User.setup: confidential`. `AgentRole.permissions: restricted`, `AgentRole.memories: confidential`, `AgentRole.allowedTools: restricted`. `AgentTask.prompt: confidential`, `AgentTask.plan: internal`, `AgentTask.outcome: internal`. `AgentMemory.text: confidential`. `BusinessEntity.properties: internal`. `SOP.steps: internal`. **Sin `salaryGross`/`salaryNet`/`bankAccount`** (no existen).
- **`AgentGovernance` sobre PDP** (F2.10): `canExecuteTool(actor, tool)` y `canExecuteAction(actor, action, policyAction)` llaman al PDP. Heredan de `AgentRole.permissions` y `AgentRole.allowedTools`.
- **`x-user-id` eliminado como fuente de verdad** (F2.11): `userHeaderMiddleware` ya no se monta o solo se monta para debugging local. `ctx.userId` es la fuente. `c.set("owner", actor.id)` para compatibilidad con handlers existentes.
- **`withRead`/`withWrite` en todas las rutas** (F2.12, D2 corregida): 14 ficheros de handlers + workers + acciones internas + streams + rutas alternativas. Se registra el mecanismo de authz de cada ruta.
- **`audit-entries` con `field`, `classification`, `allowed`** (F2.13, D12 corregida): `StoreAuditStore` acepta estos campos en `payload`. **No registra valores completos** de campos `restricted`/`secret`, solo `allowed: false` y `field`.

### Patchset F2.3 — `apps/server/src/engine/authz/pdp.ts`

**Fichero:** `apps/server/src/engine/authz/pdp.ts` (CREATE)
**Marca:** `POLICY_DECISION_POINT_V1`

**Contenido:**

```typescript
// POLICY_DECISION_POINT_V1 — evalúa políticas ABAC. Fail-closed. Deny-overrides.
// Envuelve PolicyEngine cuando el rol tiene permisos declarados.
// La autorización se aplica en handlers, workers, acciones internas,
// streams y rutas alternativas. No middleware global como única defensa.
import type {
  Policy, PolicyAction, PolicyCondition, PolicyDecision, PolicyResource, PolicySubject,
} from "../../../../../packages/domain/src/policy.ts";
import type { PolicyEngine } from "../policy/engine.ts";
import type { Actor } from "../../../../../packages/domain/src/actor.ts";

export interface PolicyContext {
  tenantId: string;
  actor: Actor;
  sessionId?: string;
  requestId?: string;
}

export interface PolicyTarget {
  ownerId?: string;
  taskScope?: string;
  assignedBy?: string;
  classification?: "public" | "internal" | "confidential" | "restricted" | "secret";
}

export class PolicyDecisionPoint {
  constructor(
    private readonly policies: Policy[],
    private readonly engine?: PolicyEngine,
  ) {}

  async can(
    ctx: PolicyContext,
    action: PolicyAction,
    resource: PolicyResource,
    field: string | undefined,
    target: PolicyTarget,
  ): Promise<PolicyDecision> {
    const applicable = this.policies.filter(
      (p) => p.resource === resource
        && p.action === action
        && this.subjectMatches(p.subject, ctx.actor)
        && this.fieldMatches(p.field, field),
    );
    let sawAllow = false;
    for (const p of applicable) {
      const decision = p.condition ? this.evaluateCondition(p.condition, ctx, target) : "allow";
      if (decision === "deny") return "deny";
      if (decision === "allow") sawAllow = true;
    }
    // PolicyEngine como fuente adicional. Si el rol tiene permisos y el motor
    // deniega, deny. Si el motor permite, se suma a sawAllow.
    if (this.engine && ctx.actor.kind === "agent" && "roleId" in ctx.actor) {
      const roleId = (ctx.actor as { roleId: string }).roleId;
      const role = { id: roleId };
      const verdict = await this.engine.can(ctx.actor.id, role, resource, action);
      if (!verdict.allowed) return "deny";
      if (verdict.allowed) sawAllow = true;
    }
    return sawAllow ? "allow" : "deny";
  }

  private subjectMatches(subject: PolicySubject, actor: Actor): boolean {
    if (subject.actorId && subject.actorId !== actor.id) return false;
    if (subject.kind && subject.kind !== actor.kind) return false;
    if (subject.role && !actor.roles.includes(subject.role)) return false;
    return true;
  }

  private fieldMatches(policyField: string | undefined, field: string | undefined): boolean {
    if (!policyField) return true;
    if (!field) return false;
    return policyField === field || policyField === "*";
  }

  private evaluateCondition(condition: PolicyCondition, ctx: PolicyContext, target: PolicyTarget): PolicyDecision {
    switch (condition.kind) {
      case "ownedBy":
        return target.ownerId === ctx.actor.id ? "allow" : "deny";
      case "inTaskScope":
        return target.taskScope === condition.value ? "allow" : "deny";
      case "assignedBy":
        return target.assignedBy === condition.value ? "allow" : "deny";
      case "hasClassification":
        return target.classification === condition.value ? "allow" : "deny";
      default:
        return "deny";
    }
  }
}
```

## Veredicto del documento 07: todavía no lo ejecutes

La dirección es buena: introducir un punto de decisión de políticas (PDP), aplicar controles en los puntos de lectura y escritura, filtrar campos sensibles y extender la autorización a rutas, workers y acciones internas. Pero el diseño del PDP presentado en F2.3 tiene fallos de autorización que pueden hacer que el sistema deniegue acceso legítimo o permita acceso indebido. Además, la cobertura propuesta no demuestra todavía que todas las rutas queden protegidas.

No es necesario descartar la fase ni rehacer la arquitectura. Sí conviene corregir los contratos centrales antes de desplegar los 32 patchsets.

## 1. Bloqueos técnicos del diseño

### A. El PDP puede permitir todo a un agente

En F2.3 aparece esta lógica:

```
const role = { id: roleId };
const verdict = await this.engine.can(ctx.actor.id, role, resource, action);
```

El anexo A.1 del propio documento indica que `PolicyEngine.can()` devuelve permiso cuando el rol no tiene `permissions` o tiene una lista vacía. Como el PDP construye un rol que solo contiene `id`, puede convertir la ausencia de permisos en una autorización positiva.

Esto contradice el principio fail-closed.

Corrección necesaria: el PDP debe resolver el `AgentRole` real y sus permisos efectivos, no construir un objeto incompleto. Si no puede resolver el rol, su estado o sus permisos, debe denegar. Además, `owner` no debe sustituirse por `actor.id` sin verificar qué ámbito espera el motor.

### B. Las políticas no aplican el tenant

`PolicyContext` contiene `tenantId`, y `Policy` admite `tenantId`, pero `PolicyDecisionPoint.can()` no comprueba que la política corresponda al tenant del contexto.

Eso deja sin aplicar una condición esencial del aislamiento multiusuario.

Corrección necesaria: definir y comprobar el tenant del contexto y del recurso en cada decisión. Una política de otro tenant nunca debe conceder acceso. Si falta el ámbito necesario para decidir, denegar.

### C. El modelo de políticas no representa realmente el efecto de una política

El esquema declara:

```
export const policyDecisionSchema = z.enum(["allow", "deny"]);
```

Pero `Policy` no contiene un campo `effect` o equivalente. En el PDP, toda política coincidente sin condición se interpreta como `allow`.

Por tanto, aunque el comentario anuncia deny-overrides, el modelo no permite expresar de manera explícita una política de denegación. Solo puede denegar cuando una condición evaluada resulta falsa.

Corrección necesaria: incorporar un efecto explícito (`allow` o `deny`) a cada política, definir precedencia y aplicar la denegación explícita con prioridad. La ausencia de una política coincidente debe seguir denegando.

### D. Las clasificaciones de campos están modeladas de forma ambigua

El documento plantea clasificaciones diferentes para varios campos de un mismo registro:

- `User.email`: `internal`.
- `User.name`: `internal`.
- `User.setup`: `confidential`.

Sin embargo, propone añadir `fieldClassification?: fieldClassificationSchema` al esquema del registro, y ese esquema representa una sola clasificación. Así no se puede expresar correctamente la clasificación de cada campo.

Hay además un riesgo de seguridad si el propio usuario puede modificar la clasificación almacenada para rebajarla y acceder a datos que deberían seguir protegidos.

Corrección necesaria: mantener un mapa de clasificación por recurso y campo, controlado por el servidor. El filtrado debe usar esa definición confiable, no una clasificación arbitraria enviada por el cliente o contenida en datos modificables.

### E. `PolicyAction` no incluye `execute`

El modelo de F2.1 enumera `read`, `create`, `update`, `delete`, `approve`, `export`, `assign` y `escalate`, pero `AgentGovernance` necesita autorizar la ejecución de herramientas y acciones.

El contrato actual no define cómo representar esa operación. No debe suponerse que `execute` equivale a `create` o `update`.

Corrección necesaria: acordar las acciones que realmente usa el código existente, incluir las necesarias en el modelo y mapearlas explícitamente desde `AgentGovernance` y `PolicyEngine`.

## 2. `withRead` y `withWrite` no bastan por sí solos

El documento acierta al exigir controles en handlers, workers, acciones internas, streams y rutas alternativas. Pero envolver `db.get()` y `db.list()` no demuestra que todas esas vías queden protegidas.

Hay tres condiciones adicionales:

- Ámbito de almacenamiento: `actor.id`, `owner` y `tenantId` son conceptos distintos. No se debe sustituir automáticamente el propietario o la partición de almacenamiento por el ID del actor.
- Datos derivados: las búsquedas RAG, agregaciones, resultados de herramientas y respuestas serializadas también deben filtrar los campos sensibles. Un resultado puede exponer información aunque su lectura original se haya autorizado.
- Configuración: `authzEnabled: false` hace que los wrappers pasen sin autorización, y `fieldClassificationEnabled: false` desactiva el filtrado. En producción no debe existir un interruptor que convierta silenciosamente estas defensas en pass-through.

La solución es definir el contrato de cada wrapper —contexto, recurso, acción, tenant, objetivo, resultado y auditoría— y comprobarlo en cada punto de acceso real. El middleware global puede aportar contexto o una protección adicional, pero no sustituye una decisión específica sobre el recurso.
