## 2. Qué conseguimos con esta fase

- **`logContext` con `tenantId`** (F04.10a/b): el middleware `requestLogger` deja de tener un `logContext` solo con `correlationId`; ahora, si el llamador le pasa un `getTenantId(owner)`, el `logContext` incluye `tenantId` en todos los logs de esa request. `app.ts` pasa `getTenantId: (owner) => tenantService.tenantIdFor(owner)`.
- **`AgentService` gana un campo `rateLimiter` público** (N05), construido en `createApp` y pasado al constructor. Con eso, `ConversationAgent` puede usar `this.service.rateLimiter.takeForTenant(tenantId, owner, "chat.message")`.
- **`takeForTenant` cableado en chat** (F04.16a): antes de cada turno en `ConversationAgent.run()`, se toma un intento; si se agota, el chat devuelve un error de cuota sin llamar al LLM.
- **`takeForTenant` cableado en RAG** (F04.16b): antes de `/api/rag/search`, se toma un intento por tenant+owner; si se agota, 429 con `Retry-After`.
- **`takeForTenant` cableado en threads** (F04.16c): antes de crear un thread (`POST /api/threads`), se toma un intento; si se agota, 429.
- **`takeForTenant` NO se cablea en browser/computer** en esta fase: F04.17 va a Fase 6 (B7), porque comparte el `tenantLimiter` con F04.16d y tiene más superficie (browser tiene `create/navigate/reopen`, computer tiene `execute/file`). Se anota en `-pendientes.md`.
- **Cero cambios de comportamiento en clone-por-cliente** con `MULTI_TENANT_SHARED != "true"` y con `rateLimiter` con límites altos (configurables por env). Los límites por defecto de `RateLimiter` en `createApp` son **no restrictivos** para no romper tests ni dev. En producción, se configuran por env.

Pero `kernelTurnPromise` se lanza con `void` y el rate limit debe aplicarse **antes** de cualquier trabajo de LLM. **El sitio correcto es dentro del IIFE async, justo después de resolver `tenantId`, antes de abrir el turno.** Si el rate limit falla, se lanza un error que el IIFE captura (ya hay un catch genérico que hace `backgroundFailure`), pero no queremos que el chat continúe. **Solución:** añadir un early-exit dentro del IIFE que emita `RUN_ERROR` y `subscriber.complete()` directamente. Pero el IIFE no tiene acceso al `subscriber` (es de `run(input): Observable`). **Alternativa más limpia:** el rate limit se hace **antes de `kernelTurnPromise`** en la parte síncrona de `run()`, justo después de `const forceDelegate = shouldDelegateToSlow(promptText);` y antes de `if (this.service.kernel)`. Ahí ya tenemos `this.owner` y podemos resolver `tenantId` con `this.service.tenantService.tenantIdFor(this.owner)` (que ya se hace más abajo, pero duplicado). Si no `allowed`, emitir error.

**Nota:** `run()` no es `async`, pero puede hacer `return new Observable(...)` con un pre-check síncrono. **El check se hace síncrono con `this.service.rateLimiter.takeForTenant(...)` (que es síncrono) y si no `allowed`, el Observable devuelve un error y termina.** Esto evita el problema de "async IIFE no puede emitir al subscriber".

**Ancla de F04.16a pasa a ser**:
```
    const forceDelegate = shouldDelegateToSlow(promptText);
```

Y se inserta después.

**Decisión confirmada:** aplicar F04.16a con ancla `const forceDelegate = shouldDelegateToSlow(promptText);` (1×).

### N08 — `request-logger.ts`: `getTenantId` opcional (2 hunks)

**Fichero:** `apps/server/src/middleware/request-logger.ts`
**Marca:** `LOG_CONTEXT_TENANT_V1`.

**Hunk N08a — firma de `requestLogger`.**

**`$old`:**
```
export function requestLogger() {
```

**`$new`:**
```
export interface RequestLoggerOptions {
  /** LOG_CONTEXT_TENANT_V1 — resuelve el tenantId del owner para incluirlo en logContext. */
  getTenantId?: (owner: string) => Promise<string>;
}

export function requestLogger(options: RequestLoggerOptions = {}) {
```

**Hunk N08b — cuerpo `withLogContext`.**

**`$old`:**
```
    await withLogContext({ correlationId }, async () => {
      logInfo("http.request", { method, path });
```

**`$new`:**
```
    // LOG_CONTEXT_TENANT_V1 — si options.getTenantId está presente y ya hay
    // owner en el contexto (por el middleware de auth que corre antes), se
    // resuelve el tenantId y se incluye. Si no, comportamiento anterior.
    const preCtx = logContext.getStore();
    let tenantId: string | undefined;
    if (options.getTenantId && preCtx?.owner) {
      try { tenantId = await options.getTenantId(preCtx.owner); } catch { tenantId = undefined; }
    }
    await withLogContext(
      { correlationId, ...(tenantId ? { tenantId } : {}), ...(preCtx?.owner ? { owner: preCtx.owner } : {}) },
      async () => {
        logInfo("http.request", { method, path });
```

**Verificación pre:** `const forceDelegate = shouldDelegateToSlow(promptText);` 1×. Si 0×, el fichero cambió, abortar F04.16a y anotar.

**Nota:** `run()` no es `async`, pero el rate limit se resuelve **antes** del `new Observable`. **La línea `const tenantIdForRate = ... await ...` requiere que `run()` sea async o que se mueva dentro del Observable.** **Corrección:** `run()` no es async, por lo que **no se puede `await` en el cuerpo síncrono**. Se mueve el rate limit dentro del `new Observable` que ya existe, justo antes del `void (async () => { ... })();`. Pero entonces el `subscriber.next` de error tiene que estar dentro del Observable. **Solución:** el check del rate limit se hace con el `tenantId` resuelto de forma síncrona solo si `tenantService` está disponible; si no, se usa `this.owner` como tenantId (aceptable para clone-por-cliente, donde todo es "default"). **La llamada a `tenantIdFor` no es imprescindible para el rate limit** porque el `RateLimiter` usa la clave `${tenantId}:${userId}:${action}` y en clone-por-cliente `tenantId=this.owner` colisiona poco (cada owner es su propio tenant). **Alternativa más limpia:** `takeForTenant(this.owner, this.owner, "chat.message")` (owner como tenantId). En shared, `this.owner` es el `ownerId`, no el `tenantId`, así que la clave sería distinta de la usada en RAG/threads. **Esto rompe la consistencia.**

**Solución final:** `run()` sí puede ser `async` internamente sin romper la firma `run(input): Observable`. La firma pública no cambia: devuelve un `Observable`. Dentro, el pre-check se hace **dentro del Observable**, en el `start(controller)` del Observable o en el `void (async () => {...})();` que ya existe. **Pero el error de rate limit debe impedir el LLM.** El sitio natural es: **en el `new Observable((subscriber) => { ... })`**, antes de `void (async () => { ... ragContext ... })();`, se hace:

```
      void (async () => {
        const tenantIdForRate = this.service.tenantService
          ? await this.service.tenantService.tenantIdFor(this.owner).catch(() => this.owner)
          : this.owner;
        const rateVerdict = this.service.rateLimiter.takeForTenant(tenantIdForRate, this.owner, "chat.message");

          subscriber.next({ type: EventType.RUN_ERROR, message: "Has alcanzado el límite..." });
          subscriber.complete();
          return;
        }
        // ... resto del IIFE (ragContext, enrichedInput, etc.) ...
      })();
```

**Pero eso requiere reescribir el cuerpo del `new Observable`**, no es un hunk de 1 línea. **Alternativa aceptable:** hacer el rate limit síncrono antes de devolver el Observable, sin `await`:

```
    // TAKE_FOR_TENANT_CHAT_V1 — pre-check síncrono con tenantId = owner (aceptable
    // en clone-por-cliente; en shared se refina en Fase 6 con el tenantId real del kernel).
    const rateVerdict = this.service.rateLimiter.takeForTenant(this.owner, this.owner, "chat.message");

        subscriber.complete();
      });
    }
```

**Esto usa `this.owner` como `tenantId`, que en clone-por-cliente es aceptable** (cada owner tiene su propio rate bucket). En shared, el bucket sería `owner:owner:chat.message` en lugar de `tenant:owner:chat.message`. Se anota como **deuda** en `-pendientes.md` para Fase 6 (con F04.17), donde se unifica el tenantId real del kernel. **Es la solución menos invasiva y funcionalmente correcta para clone-por-cliente.**

**Decisión final para F04.16a:** pre-check síncrono con `this.owner` como tenantId. Se anota la deuda.
