# Informe de fases — Event Bus + Centro de Control

> Contraste contra el repo real (`uniscrolliabrain-cloud-agente`, repodump `8a5edab`).
> Sin asumir nada previo. Cada fase es un bloque cerrado, aplicable, con typecheck.
> Horizonte: kernel Pydantic + Jev AI + k3s + OTel + Kafka. Hoy no se implementan, pero se deja el sitio.

---

## Principios que gobiernan todo el diseño

1. **El bus no es un log, es un contrato.** Eventos con `id`, `schemaVersion`, `type` cerrado, `source`, `correlationId`, `causationId`, `payload` validado.
2. **Append-only.** El bus solo `insertIfAbsent`. Nunca `put`, nunca `remove` en caliente. Purga por retención en `maintain`.
3. **Validación al emitir, no al leer.** Zod hoy, kernel Pydantic/Jev AI mañana. El punto de validación existe desde el día uno.
4. **Transporte pluggable.** `EventSink` como interfaz, `StoreSink` como implementación hoy, `KafkaSink` mañana.
5. **Observabilidad separada del dominio.** Eventos de negocio y trazas OTel son dos canales. No se mezcla `traceId` con `taskId`.
6. **El chat no ve el sistema, ve un resumen curado.** Máximo 800 tokens por turno, 5 items por tool, proactividad fuera del chat.

## Fase 1 — Event Bus global

**Objetivo**: crear el bus. No toca worker, ActionService, ni chat.

**Ficheros nuevos**:

| Fichero | Contenido |
|---|---|
| `apps/server/src/engine/events/types.ts` | `SystemEvent<T>`, `SystemEventType` (enum cerrado), `EventSource`, `EventSink`, `EventQuery`, `EventFilter`, `TimeWindow`, `Aggregate`. |
| `apps/server/src/engine/events/ulid.ts` | Generador ULID sin dependencia (~30 líneas: timestamp base32 + random). |
| `apps/server/src/engine/events/schema-registry.ts` | `EventSchema<T>`, `SchemaRegistry` con `register`, `get(type, version)`, `list()`. |
| `apps/server/src/engine/events/schemas.ts` | Zod schemas por tipo. Empieza con los tipos de Fase 1 (task, sop, action, monitor, system, auth). |
| `apps/server/src/engine/events/bus.ts` | `EventBus` con `emit`, construye el evento, valida contra registry, llama al sink. Dedupe en memoria + persistido en `records/dedupe-state` (LRU 64 entradas). |
| `apps/server/src/engine/events/sinks/store.ts` | `StoreSink` con `write` (insertIfAbsent en `kind = "system-events"`) y `StoreQuery` con `recent`, `aggregate`. |
| `apps/server/src/engine/events/index.ts` | Re-exports. |

**Ficheros modificados**:

| Fichero | Cambio |
|---|---|
| `apps/server/src/db.ts` | Índice `(owner, kind, (data->>'type'), updated_at DESC)` para `system-events`. Se añade en `createStore`, no cambia lógica. |
| `apps/server/src/engine/worker.ts` | `ctx.event` llama **además** a `bus.emit` con `task.status`, `task.failed`, `task.completed`, `step`. No se sustituye `run-events`, se añade. |
| `apps/server/src/engine/sop-executor.ts` | `sop.step.started`, `sop.step.completed`, `sop.step.skipped`, `sop.failed`. |
| `apps/server/src/actions.ts` | `action.proposed`, `action.approved`, `action.denied`, `action.executed`, `action.failed`, `action.unknown`. **Los 5 puntos de salida de `decide`**. |
| `apps/server/src/engine/service.ts` | `task.created`, `task.controlled`, `task.answered`, `system.maintenance`. `emit` en `createTask`, `control`, `answer`, `maintain`. Inyección del bus en el constructor. |

**Tipos de evento (cerrado, `schemaVersion: "1.0"`)**:
- `task.created`, `task.status`, `task.failed`, `task.completed`, `task.controlled`
- `sop.step.started`, `sop.step.completed`, `sop.step.skipped`, `sop.failed`
- `action.proposed`, `action.approved`, `action.denied`, `action.executed`, `action.failed`, `action.unknown`
- `monitor.check`, `monitor.changed`, `monitor.failed`
- `system.startup`, `system.error`, `system.maintenance`, `system.google_disconnected`
- `auth.login`, `auth.login_failed`

**Reglas**:
- `emit` fire-and-forget controlado: no lanza, loguea con `backgroundFailure` si falla.
- Eventos críticos (`task.failed`, `sop.failed`, `monitor.failed`, `action.unknown`, `system.error`) se emiten **antes** del checkpoint, no después.
- Retención: `purgeOlderThan("system-events", 90)` ya en `maintain()`.
- `correlationId` lo pasa el emisor, no lo genera el bus.
- `EventSink` se separa en `EventSink` (write) + `EventQuery` (read).

**Typecheck**: `pnpm typecheck`.

**Ledger**:
```
NEW events/types.ts, events/ulid.ts, events/schema-registry.ts,
    events/schemas.ts, events/bus.ts, events/sinks/store.ts, events/index.ts
MOD db.ts (índice), worker.ts, sop-executor.ts, actions.ts, service.ts
```

**Verificación**: `pnpm test` + manual: crear tarea, `db.list(owner, "system-events")` devuelve eventos.

## Fase 4 — Chat con acceso al sistema (contrato)

**Objetivo**: 4 tools de lectura, aditivas, con presupuesto de tokens.

**Ficheros**:
- **MOD** `apps/server/src/engine/conversation.ts` — añadir 4 tools al array.
- **MOD** `apps/server/src/engine/service.ts` — `systemContext(owner)` que devuelve objeto tipado con topes declarados por campo.

**Tools** (todas de lectura):
1. `list_pending_approvals` — máx 5.
2. `recent_events` — agregado últimas N horas, contadores + 3 ejemplos.
3. `system_health` — 4 booleanos (`google`, `worker`, `computer`, `model`) + detalle.
4. `who_is_doing_what` — máx 10 filas.

**Inyección de contexto**:
- En `conversation.ts`, antes del modelo, calcular `systemContext`.
- Si hay ≥1 aprobación pendiente o ≥1 tarea fallida desde último turno → bloque de 3 líneas (máx 80 tokens).
- Si no → nada.
- Presupuesto total: 800 tokens, campos acotados por constante, verificable por construcción.

**Reglas del prompt** (añadir al system prompt):
- No ejecutes acciones proactivamente.
- Si el usuario dice "haz lo que haga falta", pide que elija.
- No repitas estado del sistema si no te lo piden.
- Nunca más de 5 items por tool.

**Typecheck**: `pnpm typecheck`.

**Ledger**:
```

```

**Verificación**: manual.
