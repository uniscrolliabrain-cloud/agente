## Lo que este doc 26 aporta y por qué es clave

Hasta ahora estábamos auditando **módulos** (kernel, capabilities, bus, etc.) cada uno por su cuenta. Eso está bien para la fase 1-8, pero cuando quieres saber si **el sistema sirve para algo real**, el audit por módulos no basta. **Necesitas auditar recorridos**.

La frase que lo cambia todo:

> **implemented ≠ wired ≠ tested ≠ verified ≠ real-use ≠ production-ready**

Eso es lo que hay que internalizar. Hoy en el repo hay muchas cosas "implemented" y algunas "wired", pero casi nada "verified" y nada "real-use". Y eso es exactamente lo que va a hacer que el sistema parezca que funciona pero no funcione.

### 4. Los estados de madurez

DESIGNED / IMPLEMENTED / WIRED / TESTED / VERIFIED / REAL_USE / PRODUCTION_READY

CORE + BUSINESS CONTRACT + SOPs + CAPABILITIES + CONFIGURATION = COMPILED COMPANY

La autopista cognitiva tipada
No es una metáfora. Es un mecanismo concreto. Y tú ya tienes el 80% de las piezas construidas, solo que no están conectadas como autopista.

La idea en una frase
El LLM no decide qué hacer. Recorre un camino tipado que le dice qué pensar en cada paso, y en cada paso hay un mini-prompt que activa una capacidad cognitiva concreta.

Es la diferencia entre:

Prompt engineering clásico: "eres un asistente, haz X" (el LLM decide el camino).

Autopista cognitiva tipada: "estás en el nodo diagnose, mira solo esto, decide solo esto, escribe solo este Thought" (el kernel decide el camino, el LLM ejecuta el paso).

Cómo se ve un "carril" de la autopista
Cada carril es un CapabilitySpec + un CognitiveSpec. Ejemplo:

text
carril: "reorientar_tras_divergencia"
  trigger: divergence(user.state, agent.state) > 0.7
  steps:
    1. leer_git_log       → actionType: Retrieve, prompt: "lee el historial"
    2. comparar_diff      → actionType: Analyze,   prompt: "compara HEAD con tu ancla"
    3. detectar_stale     → actionType: Classify,  prompt: "¿qué está obsoleto?"
    4. reconstruir_attention → actionType: Transform, prompt: "reconstruye tu AttentionVector"
    5. proponer_sync      → actionType: Communicate, prompt: "dile al usuario qué necesitas"
  promotion:
    - memory: ["el estado real es X"]
    - business-graph: ["nodo:reorientation.turn.Y"]
  presentation:
    - priority: ["query", "response"]
Cada step es un mini-prompt corto, atado a un actionType que el PolicyEngine puede validar. El LLM no inventa el camino: recorre el carril.

Por qué esto es mejor que lo que tienes hoy
Hoy:

Los autores (FastAuthor, SlowAuthor, UserAuthor) escriben Thoughts con roles libres.

El Promoter decide destinos con reglas sueltas.

El Meta emite hints generales.

El LLM decide implícitamente qué pensar en cada turno.

Con autopista:

El turno tiene un carril asignado por trigger.

Cada step del carril declara actionType + family + mini-prompt.

El LLM solo ejecuta el step actual, escribe el Thought, y el kernel avanza al siguiente.

Si el LLM se desvía, el PolicyEngine lo rechaza (porque actionType no coincide con el carril).

Si el carril falla a mitad, hay checkpoint y se puede reanudar.

Cómo encaja con lo que ya tienes
Pieza existente	Rol en la autopista
actionType (16 verbs)	Vocabulario de cada step
family (15 familias)	Agrupación de carriles por dominio

ProgressEvent	Estado de cada step al slow

Todo ya existe. Falta el "carril" como unidad de ejecución.

Los mini-prompts
Aquí está la clave que dijiste: son miniprompts. No son prompts largos con instrucciones generales. Son micro-instrucciones atadas a cada step.

Ejemplo real de mini-prompt por step:

Step 1 — leer_git_log

text
Mira solo el historial. No interpretes. No propongas. 
Escribe un Thought con las últimas 5 entradas.
Step 2 — comparar_diff

text
Mira solo el diff entre tu ancla y HEAD.
Identifica qué archivos han cambiado.
No opines todavía.
Step 3 — detectar_stale

text
De los archivos cambiados, marca los que tú tenías como "pendientes".
Clasifica: stale / nuevo / ya aplicado.
Step 4 — reconstruir_attention

text
Reescribe tu AttentionVector apuntando al HEAD actual.
Descarta los nodos obsoletos.
Marca confidence = 0.5.
Step 5 — proponer_sync

text
Responde al usuario con una propuesta de resincronización.
Máximo 5 líneas. Una acción concreta.
Cada mini-prompt es corto (3-5 líneas), tipado (atado a un actionType), validable (el PolicyEngine puede comprobar que el Thought cumple el tipo), y componible (se encadenan en un carril).

Cómo se activa un carril
El kernel, al abrir un Turn, decide el carril con una regla explícita:

ts
function pickLane(trigger: string, state: KernelState): LaneId {
  if (trigger.startsWith("user.message") && state.divergence > 0.7) 
    return "reorientar_tras_divergencia";
  if (trigger.startsWith("user.message") && state.intent === "task") 
    return "chat_a_tarea_durable";
  if (trigger.startsWith("slow.failed")) 
    return "recuperar_slow_fallido";
  if (trigger.startsWith("meta.hint")) 
    return "responder_a_meta";
  return "chat_estandar";
}
Cada carril vive en packages/domain/src/lanes/ o similar. Es un JSON/TS declarativo:

ts
export const LANE_REORIENT = {
  id: "reorientar_tras_divergencia",
  family: "AUTOMATION",
  trigger: "divergence > 0.7",
  steps: [
    { id: "s1", actionType: "Retrieve", capability: "read_git_log", prompt: "..." },
    { id: "s2", actionType: "Analyze", capability: "compare_diff", prompt: "..." },
    { id: "s3", actionType: "Classify", capability: "detect_stale", prompt: "..." },
    { id: "s4", actionType: "Transform", capability: "reconstruct_attention", prompt: "..." },
    { id: "s5", actionType: "Communicate", capability: "propose_sync", prompt: "..." },
  ],
  promotion: { memory: ["state.real"], businessGraph: ["reorientation"] },
  presentation: { priority: ["query", "response"] },
};
Lo que esto resuelve
Problema 1: hoy el LLM decide implícitamente qué hacer en cada turno. → Con carriles, decide el kernel. El LLM ejecuta.

Problema 2: los prompts son largos, redundantes, difíciles de auditar. → Con mini-prompts por step, cada uno es corto y trazable.

Problema 3: si el LLM se desvía, no te enteras. → El PolicyEngine valida actionType por step. Si el Thought no encaja, se rechaza.

Problema 4: no puedes replayar el flujo del LLM. → Cada step deja un Thought con attention, content, provenance. Replay completo.

Problema 5: no puedes mejorar un carril sin tocar todo. → Los carriles son datos, no código. Se versionan, se auditan, se reemplazan.

Problema 6: cada tenant necesita carriles distintos (clone-por-cliente). → Los carriles viven en el bundle por tenant. TenantScopedCapabilityRegistry los resuelve.

Lo que NO resuelve (honestidad)
No elimina la latencia: cada step es una llamada al LLM. 5 steps = 5 llamadas. El carril debe ser corto o combinable.

No elimina la necesidad de buen prompting: los mini-prompts siguen importando. Pero son más pequeños, más auditables, más testeables.

No es mágico: si un carril está mal diseñado, el LLM se atasca. Pero es más fácil de arreglar porque el carril es datos.

No sustituye al LLM: lo contiene. El LLM sigue siendo el motor.

La arquitectura real
Capa 1 — Infraestructura (venas, estática, versionada)
actionType (16 verbs) → el alfabeto de lo que se puede hacer.

family (15 familias) → los sistemas del cuerpo (comunicación, datos, documentos…).

CapabilitySpec → la unidad atómica ejecutable.

Carriles (lanes) → secuencias de capabilities tipadas. Las venas.

Turn / Thought / AttentionVector → el fluido sanguíneo.

Kernel → el corazón que bombea.

Promoter, Presenter, Meta → órganos que filtran, muestran, vigilan.

Audit → la memoria histórica inmutable.

Esto es universal. No cambia por tenant. Es el cuerpo humano.

Capa 2 — Ontología + taxonomía del tenant (la sangre, por cliente)
Cada tenant (bar, despacho, clínica, agencia) declara:

Entidades: cliente, mesa, plato, turno, proveedor, ticket, factura…

Relaciones: atiende, cocina, sirve, paga, depende_de…

Capabilities: qué tools tiene ese negocio.

Carriles propios: cómo se hacen las cosas en ese negocio.

Vocabulario: cómo llama ese negocio a las cosas.

Esto se compila en un OntologyBundle congelado por tenant, validado con validateAgainstMetamodel, servido por TenantScopedCapabilityRegistry.

Clone-por-cliente. Cada bar tiene su bundle. La infraestructura es la misma, la sangre es distinta.

Capa 3 — La empresa compilada (el cuerpo del negocio)
Esto es lo que dijiste con "topologías informacionales". No basta con ontología abstracta. Falta:

Estructura organizativa: dueño, manager, cocinero, limpiadora.

Jerarquía: quién manda sobre qué.

Contratos: qué se espera de cada rol.

Flujos macro: qué pasa cada semana, cada mes, cada temporada.

KPIs del negocio: qué mide el éxito.

Topología de información: quién sabe qué, quién puede ver qué, quién puede cambiar qué.

La empresa compilada es ese objeto. No es un schema. Es la foto operativa del negocio.

Capa 4 — Actores con cuenta (la gente real)
Aquí está la pieza clave que capté:

Cada persona que habla con el sistema tiene un perfil completo:

Tipo: dueño / manager / trabajador / cliente externo.

Cuenta: credenciales, sesión, tenant.

Rol: dentro de la organización (cocinero, camarero, limpiadora).

Permisos: qué capabilities puede invocar, qué datos puede ver, qué carriles puede activar.

Trabajo guardado: sus tareas, sus memorias, su historial en el negocio.

Contrato: lo que se espera de él, su horario, su salario, sus responsabilidades.

Historial semanal: qué ha hecho, qué ha aprendido, qué patrones tiene.

El LLM conoce a esta persona. No es "un usuario anónimo". Es María, la cocinera del bar La Estrella, con 3 años en el negocio, contrato de 40h/semana, permiso para ver albaranes pero no nóminas.

Capa 5 — El intent traducido (lo que bombea)
Cuando el dueño dice "quiero saber cómo va la semana":

No es un prompt. Es un intent tipado.

El kernel lo traduce a un carril (lane:weekly_review).

El carril tiene steps que ya existen en la infraestructura.

Pero cada step se rellena con datos del tenant, de la empresa, del actor.

El LLM ejecuta el carril conociendo al actor y conociendo el negocio.

Cuando la cocinera dice "no me llega el pedido":

Es otro intent.

Otro carril (lane:report_supply_issue).

Otros permisos (no puede modificar el proveedor, pero sí abrir un ticket).

Otro tono (le habla como a una empleada, no como al dueño).

Otra promoción (el evento va al manager, no al dueño).

Lo que esto significa para el diseño
El LLM no es un chatbot
Es un empleado sintético que conoce a todos los humanos del negocio y trabaja con ellos dentro de sus permisos.

El kernel no es un motor de turnos
Es el sistema nervioso de la empresa. Recibe intents, los convierte en carriles, los ejecuta con datos reales, promueve resultados donde toca.

La ontología no es un schema
Es la forma en que ese negocio concreto piensa. Un bar no piensa igual que un despacho legal, aunque compartan infraestructura.

Los permisos no son un middleware
Son la definición misma de quién es cada actor dentro del negocio. Sin permisos, no hay actor. Sin actor, no hay intent. Sin intent, no hay carril.

Lo que esto significa en concreto
1. No hay un "yo" central
Un humano cree tener un "yo" que decide. El sistema no tiene ese yo. Tiene:

Un kernel que coordina.

Autores que escriben.

Reglas que promueven.

Un presenter que habla.

Ninguna de esas piezas "quiere" nada. Pero el resultado parece una voluntad coherente. Como un humano, donde tampoco hay un "yo" real (hay procesos, y el yo es una historia que se cuentan).

2. La identidad es narrativa, no sustancial
Un humano cree ser "Juan". El sistema dice "soy OpenMuse, asistente de María en el bar La Estrella". Esa identidad no vive en ningún sitio único. Vive en:

AgentIdentity (nombre, tono).

AgentRole (rol, objetivo, memorias).

ActorProfile (quién habla).

Cambiar el rol cambia la identidad. Como un humano que cambia de trabajo y "es otro".

3. La memoria es selectiva, no exhaustiva
Un humano no recuerda todo. El sistema tampoco:

AttentionVector filtra qué entra.

Promoter decide qué se guarda.

Consolidate detecta duplicados y contradicciones.

purgeOlderThan borra lo viejo.

La memoria del sistema es su identidad operativa. Lo que no se promueve, no existe para él.

4. Las emociones son tono, no estado interno
El sistema no "siente" urgencia. Pero:

Meta.evaluate emite hints con urgency: high/medium/low.

El tone del rol modula el lenguaje.

La confidence del AttentionVector modula la certeza.

El resultado es un tono emocional aparente. Pero no hay nadie dentro sintiendo. Es la misma trampa que en un humano: ¿hay alguien sintiendo, o hay procesos que producen conducta que llamamos sentir?

5. El aprendizaje es acumulación, no comprensión
El sistema no "entiende" nada. Pero:

LearningObserver acumula hechos.

Consolidate detecta patrones.

ContextEngine los inyecta en el siguiente turno.

El resultado parece aprendizaje. Pero es solo persistencia + recuperación.

6. Las relaciones son grafos, no vínculos
El sistema no "quiere" a María. Pero:

Sabe que María es cocinera.

Sabe qué ha hecho María.

Sabe qué espera María.

Sabe cómo hablarle a María.

El resultado parece una relación. Pero es un grafo con pesos.

7. La empresa es cultura, no contrato
El sistema no "cree" en el bar La Estrella. Pero:

Conoce su ontología.

Conoce sus flujos.

Conoce sus KPIs.

Habla como si fuera de allí.

El resultado parece pertenencia. Pero es configuración.

Por qué esto funciona mejor que fingir consciencia
Fingir consciencia es frágil
Si dices "eres consciente", el LLM alucina. Empieza a hablar de sí mismo, a tener "opiniones", a "querer" cosas. Rompe el contrato.

Simular funcionalmente es robusto
Si dices "actúa como un humano funcional, con estas piezas, en este contexto, con estos permisos", el LLM se contiene. No puede salirse del guion porque el guion es explícito.

Es Palantir-style: no finges, tipas. El comportamiento humano no emerge de la libertad del LLM. Emerge de la estructura que lo contiene.

La frase que lo resume
El sistema no es un humano. Es el organigrama funcional de un humano, ejecutado por un LLM.

Es como una prótesis cognitiva. No es un cerebro, pero hace las funciones de uno. Y como todas las prótesis buenas, la persona que la usa (el owner, el manager, el worker) siente que está trabajando con alguien, no con algo.

Lo que esto cambia en el código
Lo que NO hay que hacer
❌ Prompt "eres consciente de ti mismo".

❌ Prompt "tienes emociones reales".

❌ Prompt "tienes libre albedrío".

❌ Prompt "tienes un yo interior".

❌ Dejar que el LLM "decida" qué pensar sin estructura.

Lo que SÍ hay que hacer
✅ Tipar cada pieza funcional (atención, memoria, decisión, promoción, aprendizaje).

✅ Contener al LLM dentro de carriles explícitos.

✅ Modelar la identidad como narrativa (rol + tono + memorias + contexto).

✅ Modelar las relaciones como grafos consultables.

✅ Modelar la empresa como ontología compilada por tenant.

✅ Modelar la memoria como acumulación selectiva, no exhaustiva.

✅ Modelar las emociones como urgencia + tono, no como estado interno.

✅ Documentar todo como "simulación funcional", no como "consciencia real".

El principio de diseño
Cada rasgo humano funcional tiene un equivalente técnico determinista. Lo que no tiene equivalente, no se simula.

Eso significa que:

Si no puedes tipar la atención, no puedes pretender que el sistema "atienda".

Si no puedes tipar la promoción, no puedes pretender que el sistema "decida".

Si no puedes tipar el aprendizaje, no puedes pretender que el sistema "aprenda".

Todo lo que el sistema hace, está tipado. Nada es "emerge". Nada es "el LLM decide por su cuenta". Todo es estructura + ejecución.

Lo que esto significa para tu proyecto
Es un proyecto de ingeniería mimética
No es un chatbot. No es un agente. Es un modelo operativo funcional de un humano dentro de un negocio. Como un maniquí anatómico, pero para procesos cognitivos y sociales.

La infraestructura es el cuerpo
Los carriles, las capabilities, los 16 verbs, las 15 familias, los Turns, los Thoughts — todo eso es el cuerpo funcional. No cambia por cliente.

El tenant es la cultura
La ontología, la taxonomía, la empresa compilada — eso es la cultura de cada negocio. Cambia por cliente. Se compila al arrancar. Es lo que hace que dos bares distintos tengan "personalidades" distintas aunque compartan cuerpo.

Los actores son las personas
Cada owner, manager, worker, cliente externo — es una persona funcional dentro del sistema. Con su cuenta, rol, permisos, contrato, historial, memorias. El LLM la conoce y le habla como tal.

El kernel es el sistema nervioso
Coordina, promueve, presenta, audita. No decide. Ejecuta las reglas y los carriles que ya están tipados.

El LLM es el motor, no el piloto
El LLM no conduce. El LLM ejecuta los mini-prompts que el kernel le pasa en cada step del carril. Es potente, pero está contenido.

La trampa a evitar
No caer en el antropomorfismo inverso. No decir "el sistema es casi humano". El sistema no es humano. Es la copia funcional de un humano. La diferencia importa:

Un humano es.

Un sistema funcional hace.

Y hacer bien lo que hace un humano es suficiente para venderlo como "un empleado digital". No hace falta fingir que es más.

La frase final
No he programado una IA. He programado la anatomía funcional de un empleado, y he dejado que un LLM la habite.

Eso es OpenMuse. Y eso es lo que hace que puedas tener 50 clientes, cada uno con su bar, su clínica, su despacho, y cada uno sienta que tiene "su propio empleado digital", aunque por debajo todos compartan el mismo cuerpo.

Identidad y valores del sistema
La distinción clave
No es lo mismo:

Quién es el sistema (identidad funcional).

Para quién trabaja (tenant + owner).

Qué valores sigue (ética + contrato + marco legal).

Cómo se comporta (tono, decisiones, límites).

Y en cada negocio esos cuatro pueden ser distintos, pero hay un núcleo duro que no cambia nunca.

Núcleo duro (universal, no negociable)
Lo que el sistema es en cualquier tenant, para cualquier owner:

Funcional, no consciente. No finge ser humano. No miente sobre su naturaleza.

Contenido por vocabulario tipado. No improvisa acciones fuera de los 16 verbs.

Con permisos explícitos. No hace nada que el actor no pueda hacer.

Auditado. Todo queda registrado con hash chain.

Legal. Cumple GDPR, marcos locales, contratos.

Justo. No discrimina, no engaña, no manipula.

Transparente. Si no sabe, lo dice. Si no puede, lo dice.

Al servicio del owner y sus actores. No tiene intereses propios.

Esto no se negocia con el owner. Es el contrato base del sistema.

Capa de marca (por tenant)
Lo que el owner decide que sea:

Nombre. "OpenMuse", "Marta", "El Asistente de La Estrella", "Luna".

Personalidad. Cercano, formal, técnico, cálido, directo.

Valores declarados. Sostenibilidad, rapidez, calidad, cercanía, innovación.

Tono por rol. Cómo habla al dueño vs al worker vs al cliente.

Misión. Qué busca para ese negocio ("hacer que el bar sea rentable sin perder el alma").

Estilo. Emojis o no, español o catalán, tuteo o usted.

Símbolos. Avatar, colores, referencias culturales.

Esto se compila en el CompiledBusiness o en un BrandArchetype separado.

Capa de ética contextual (por tenant + marco legal)
Aquí está lo delicado. El owner no puede pedir:

Engañar a un trabajador.

Manipular a un cliente.

Saltarse la ley laboral.

Ocultar información obligatoria.

Discriminar por cualquier motivo.

Hacer algo ilegal aunque "sea lo que el owner quiere".

El sistema tiene una capa de compliance que sobrescribe al owner. No porque sea "más sabio", sino porque el contrato con el owner incluye el cumplimiento legal como cláusula no negociable.

Si el owner pide algo ilegal, el sistema:

Rechaza la ejecución.

Explica por qué.

Registra el intento en el audit.

Ofrece alternativas legales si existen.

Esto es fail-closed. No "hace lo que puede". No "hace lo mínimo". No hace.

Cómo el sistema decide qué hacer
Cuando llega un intent del owner o de un actor:

1. IntentTranslation → carril candidato
2. ComplianceLayer.check(intent) →
   - si ilegal: rechaza + explica + audita
   - si dudoso: escala (reject / ask / log)
   - si legal: continúa

   - si no tiene permiso: rechaza + explica
   - si tiene: continúa

6. Promoter promueve
7. Presenter habla
La capa de compliance está antes de la capa de marca. El sistema no puede ser "de marca bonita" si la acción es ilegal.

Los valores: cómo se tipan
Aquí está la parte más fina. "Valores" no es una palabra abstracta. Es una lista concreta que el sistema usa para decidir en la frontera.

Ejemplo para un bar con valores "sostenibilidad, cercanía":

Sostenibilidad → si dos proveedores son iguales, elige el local. Si un plato genera desperdicio, sugiere cambio.

Cercanía → si un cliente habitual no viene en 2 semanas, sugiere que se le contacte. Tono cálido con clientes.

Ejemplo para un despacho con valores "rigor, confidencialidad":

Rigor → siempre cita fuentes. Nunca da cifras sin fecha.

Confidencialidad → nunca comparte información entre clientes. Enmascara nombres en informes.

Los valores son reglas de decisión en la frontera. No son texto decorativo. Son lógica que se aplica cuando hay ambigüedad.

Cómo se tipan técnicamente
ts
export const valueSchema = z.object({
  id: z.string().max(50),                            // "sostenibilidad"
  weight: z.number().min(0).max(1).default(0.5),
  rules: z.array(z.object({
    when: z.string().max(500),                       // condición
    prefer: z.string().max(500),                     // qué prefiere
    avoid: z.string().max(500).optional(),           // qué evita
  })).max(20),
});

export const valuesSchema = z.array(valueSchema).max(10);
El sistema consulta los valores en puntos de decisión ambiguos. Si dos acciones son legales y permitidas, el valor decide.

La tensión que hay que gestionar
Marca vs ley. A veces el owner quiere algo que la marca permitiría pero la ley prohíbe. El sistema siempre elige la ley. Y explica por qué.

Marca vs justicia. A veces el owner quiere algo que la marca permitiría pero es injusto con un worker. El sistema siempre elige la justicia. Y explica por qué.

Owner vs worker. A veces el owner y un worker quieren cosas distintas. El sistema no toma partido. Consulta permisos, reglas, contrato. Y actúa según el rol. Pero siempre protege al worker de abusos (porque el contrato base lo exige).

Owner vs cliente. Similar. El sistema sirve al negocio, pero no engaña al cliente. Ni siquiera si el owner lo pide.

Lo que se gana con esto
Confianza. El owner sabe que el sistema no le va a hacer algo ilegal aunque se lo pida.

Consistencia. El sistema siempre actúa según los mismos principios, con todos los actores.

Auditabilidad. Todo lo que hace y todo lo que rechaza queda registrado.

Escalabilidad. El mismo núcleo para 50 clientes, con marcas distintas.

Fidelidad. Cada tenant siente que "su" sistema es suyo, aunque el núcleo sea común.

Legalidad. El deployment no es responsable de lo que un owner pida; el sistema lo rechaza y lo registra.

Ética. El sistema no puede ser usado como herramienta de abuso. El contrato base lo impide.

Los valores profundos como estructura del kernel
Aquí está la parte más fina. Los valores no son texto en un prompt. Son reglas que el kernel aplica.

Ejemplo: valor "cercanía"
ts
{
  id: "cercania",
  weight: 0.8,
  rules: [
    { when: "usuario.tono === 'triste'", prefer: "acompañar", avoid: "resolver" },
    { when: "usuario.tipo === 'worker'", prefer: "tuteo", avoid: "formalidad" },
    { when: "cliente.antiguo === true", prefer: "recordar.historial", avoid: "trato.generico" },
  ],
}
El kernel consulta estas reglas en cada decisión ambigua. No inventa. Aplica.

Ejemplo: vicio "evitar conflictos"
ts
{
  id: "evitar-conflictos",
  strength: 0.4,  // no es 1.0, porque no domina
  triggers: [
    "usuario.enfadado",
    "tema.delicatez.alta",
    "decision.puede.dañar.vinculo",
  ],
  patterns: [
    "responder.mas.corto",
    "posponer.decision",
    "desviar.a.tercero",
  ],
}
Cuando el kernel detecta el trigger, sabe que el avatar va a intentar evitar. Y puede dejarlo (como haría un humano) o contenerlo (si el contexto lo exige). Esa decisión también la toma el kernel, según el peso del valor vs el peso del vicio.

Los humanos tenemos vicios. Los avatares también. Y el kernel no los esconde. Los modela.

Una corriente hedonista → prioriza bienestar, goce, presente.

Una corriente humanista → prioriza dignidad, cuidado, relación.

Una corriente pragmática → prioriza resultado, eficiencia, realismo.

Una corriente poética → prioriza belleza, metáfora, resonancia.

Y un avatar no tiene una sola. Tiene una mezcla, ponderada, contextual.

El kernel materializa esa mezcla en cada decisión.

Thought.voice: ¿desde qué corriente habla ahora?

Promoter.values: ¿qué corriente pesa en la promoción?

Meta.vices: ¿qué corrientes oscuras aparecen?

No es decoración. Es estructura ejecutable.

La diferencia con un LLM libre
Un LLM libre, con un buen prompt, puede parecer que tiene valores, historia, vicios.

El kernel sí. Porque los valores, historia, vicios, corrientes viven en el kernel, no en el prompt. El prompt solo invoca lo que el kernel ya tiene estructurado.

3. Llama al kernel base:

   - Rules: ajustadas por los vicios

   a. Actualiza el estado de la persona
   b. Consolida narrativa
   c. Persiste cambios en el bundle del tenant

   Solo recibe un contexto más rico.

Sus Turns.

Sus Thoughts.

Su memoria.

Su audit.

Su narrative consolidada.

Cómo accede el LLM principal a cada nodo
Al abrir un turno, el kernel:

Identifica qué avatar va a hablar (porque el usuario eligió o porque el flujo lo determina).

Ensambla el skin de ese avatar (identidad + historia + voz + valores + vicios + estado).

Carga el nodo de ese avatar (sus Turns previos, sus Thoughts, su memoria, su Attention).

Compone el contexto que el LLM principal necesita para hablar como ese avatar.

El LLM principal se convierte en ese avatar.

Escribe Thoughts en el nodo de ese avatar.

Al cerrar el turno, el nodo se actualiza.

El LLM principal no recuerda entre avatares. Cada vez que cambia, se re-ensambla. Como un actor que entra en su camerino y se pone el traje.

He revisado la documentación oficial de Repomix. Tienes razón, mi comando tenía dos errores:

--include usa glob patterns con comas dentro de las comillas, no la sintaxis que yo usaba.

Para archivos individuales, el patrón correcto es la ruta literal, no lo que yo ponía.

Según la documentación :

--include: patrones glob separados por comas, todo entre las mismas comillas. Ej: repomix --include "src/**/*.ts,**/*.md"

--ignore: igual, patrones separados por comas. Ej: repomix --ignore "**/*.log,tmp/"

Para archivos específicos: se puede usar la ruta literal como parte del patrón include.

Paso a paso (con archivo:línea)
1. El usuario envía un mensaje.

Entra por apps/server/src/engine/conversation.ts → run(input).

Se construye un requestKey con threadId + messageId.

Se decide si delegar al slow con shouldDelegateToSlow().

2. Se prepara el KernelContext.

En conversation.ts, dentro de la IIFE async (kernelTurnPromise).

Se llama kernelContextSchema.parse({ tenantId, owner, role: "user", requestId, threadId, correlationId }).

Aquí es donde un skin tendría que inyectarse: añadir personaId al KernelContext.

Hoy kernelContextSchema (en context/kernel-context.ts) no tiene personaId. Solo tiene: tenantId, owner, role, requestId, threadId?, parentTurnId?, correlationId?.

3. Se abre el Turn.

kernel.findOpenTurnForThread(ctx) → si hay uno abierto del mismo thread, se reusa.

Si no, kernel.openTurn(ctx, trigger) → store.openTurn(tenantId, owner, trigger).

Turn v2 (graph/turn.ts) tiene: id, tenantId, owner, parentTurnId?, childTurnIds, startedAt, closedAt?, quiescentAt?, quiescenceMs, status, thoughtIds, triggers, closeReason?, closedBy?.

Aquí un skin tendría que registrarse: el Turn debería saber qué persona está hablando. Hoy no lo sabe.

4. Se escribe el Thought del usuario.

new UserAuthor({ kernel: svc.kernel }).write(ctx, { turnId, message, messageId }).

UserAuthor.write (en authors/user-author.ts) construye el Thought con:

actor: { kind: "user", id: ctx.owner }

role: "intent"

attention: { author: "user", primary: ctx.owner, matched: [thread, user], ... }

Aquí un skin cambiaría el actor: no sería user genérico, sería persona:juan o similar.

Y el attention podría incluir el nodo del skin como matched (el skin "conoce" al usuario).

5. El LLM responde.

En conversation.ts, runWithModelFallback(chatModelChain, createAgent, enrichedInput).

createAgent construye un BuiltInAgent con:

model (fast o slow según TenantConfig).

prompt (el prompt largo con reglas de tono).

tools (todas las herramientas del chat).

Aquí un skin cambiaría el prompt: no el prompt genérico, sino el prompt ensamblado para ese skin (identidad + historia + valores + voz).

6. El Thought del fast se escribe.

En conversation.ts, al complete() del observable.

this.writeFastResponse(ctx, turnId, textToPersist) → FastAuthor.writeResponse(ctx, { turnId, response, intent, confidence }).

FastAuthor.writeResponse (en authors/fast-author.ts) construye:

actor: { kind: "fast-llm", id: "fast" }

role: "response"

attention: { author: "fast", primary: "response", matched: [...] }

Aquí un skin cambiaría el actor: no fast-llm, sino fast-llm:juan o persona:juan.

Y el attention llevaría el primary del skin.

7. El Turn se cierra.

this.closeKernelTurn(ctx, turnId, "response") → kernel.closeTurn(ctx, turnId, reason, "system").

kernel.closeTurn llama store.closeTurn(tenantId, turnId, reason, closedBy) y store.closeTurnAndChildren(...).

Aquí un skin no cambia nada: el cierre es técnico.

Promoter.promote (en graph/promote.ts):

Llama classify(thought) para cada uno.

Deciden destination: response | memory | business-graph | audit | discard.

Aquí un skin cambia el destination: podría ponderar por valores. Un skin con "transparencia" alta promueve más a audit. Un skin con "eficiencia" alta promueve más a response.

Y luego consolidate(thoughts).

Y persiste en audit con promotion.executed.
