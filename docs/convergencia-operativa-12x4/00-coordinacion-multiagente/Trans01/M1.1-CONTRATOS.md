# Trans01 · M1.1 — contratos publicados para Trans02, Trans03 y Trans04

Contratos que el kernel necesita o expone. Son aditivos sobre los tipos existentes y no crean una
segunda taxonomía. Cualquier consumidor puede adoptarlos sin migración.

## 1. `EXECUTION_OUTCOME_CONTRACT_V1` — adaptadores (Trans03)

Un adaptador declara el resultado de un efecto con un único discriminante:

```ts
type AdapterOutcomeClass =
  | "rejected_before_dispatch" // rechazo confirmado ANTES de enviar: no hubo efecto
  | "failed_without_effect"    // fallo confirmado con evidencia de no-efecto
  | "accepted"                 // el proveedor aceptó; la confirmación aún no existe
  | "confirmed"                // efecto confirmado
  | "unknown";                 // sin evidencia suficiente
```

- En un **error**: `Object.assign(new Error(msg), { outcome: "rejected_before_dispatch" })`.
- En un **resultado**: `{ outcome: "accepted", providerRef }` si solo hay aceptación.
- Sin declaración: error ⇒ `unknown`; resultado ⇒ `confirmed`.
- Compatibilidad: `outcomeUnknown: true` y `code: "outcome_unknown"` se siguen leyendo como `unknown`.
- `retrySafe` **solo** es `true` para las dos clases de no-efecto confirmado. Un `status` 4xx aislado no
  es evidencia.
- Estados del claim: `claimed → done | failed(retrySafe) | accepted | outcome_unknown`. `accepted` y
  `outcome_unknown` no se reenvían; exigen conciliación.

Pendiente de Trans03: que Gmail, Calendar, Drive, WhatsApp y computer declaren la clase en sus errores
de timeout/validación/desconexión. Hasta entonces, todo error no clasificado es ambiguo (seguro).

## 2. `APPROVAL_BINDING_CONTRACT_V1` — propuestas (trans02)

El runner exige, en la ruta gobernada, que el registro `actions` que autoriza un paso tenga:

| Campo | Regla |
|---|---|
| `tenantId` | presente e igual al tenant del `ExecutionContext` |
| `taskId` | igual a `ctx.taskId`; sin tarea en el paso, la propuesta no puede tener tarea |
| `hash` + `revision` | presentes: la aprobación está atada a una revisión revisada |
| `expiresAt` | futuro |
| `principal` | igual a `ctx.actorId` o al owner autenticado |
| `connectionGeneration` | obligatorio para efecto externo |
| `capabilityId` | si existe, igual a la capability ejecutada |
| `data` / `kind` | si el paso declara `data`/`kind`, coincidencia exacta |

Además, una aprobación `succeeded` solo se reutiliza para el **mismo paso** (claim `done`); cualquier
otro paso responde `approval already consumed`.

Solicitud a trans02 en la ruta de `propose`: añadir `capabilityId` a la propuesta (hoy no lo conoce) para
cerrar el binding por operación sin depender del `kind`. Mientras no exista, el binding cubre tenant,
tarea, contenido, principal, caducidad, conexión y consumo único.

El contexto de ejecución acepta `approvalId?: string`. `sessionId` sigue funcionando como fallback
histórico, pero una sesión no es una aprobación.

## 3. `EVENTS_ACTOR_PROVENANCE_V1` — bus (trans02/Trans04)

- `EmitOptions.actorKind?: "human" | "service"`; `SystemEvent.actorKind` se persiste.
- Perfil causal-1 (`causal` presente):
  - con scope de petición, el actor es `currentTenantScope().actorId`; un `actorId` distinto ⇒
    `ACTOR_NOT_AUTHENTICATED`;
  - sin scope, solo se admite `actorKind: "service"` con id `service:<nombre>` y `source.kind` en
    `{system, kernel, monitor}`;
  - `source.personaId` nunca es actor (`PERSONA_IS_NOT_AN_ACTOR`);
  - `actorKind: "service"` dentro de un scope humano ⇒ `ACTOR_KIND_MISMATCH`.
- Eventos sin `causal` conservan el comportamiento histórico y **no** reciben garantías retroactivas.

## 4. `KERNEL_TELEMETRY_HOOKS_V1` — Trans04 (T04-H01)

```ts
interface KernelObservation {
  stage: "kernel.decision" | "kernel.denial" | "runtime.claim" | "runtime.result"
       | "runtime.reconciliation" | "bus.commit" | "bus.rollback";
  status: "ok" | "denied" | "failed" | "unknown";
  durationMs: number;
  correlationId?: string; // enlace interno, NO etiqueta exportable
  capabilityId?: string;  // id registrado, no payload ni id de negocio
  errorClass?: string;    // clase enumerada, sin mensaje del proveedor
}
```

`registerKernelTelemetrySink(sink)` devuelve la función de baja. La publicación es síncrona y sin
`await`; un sink caído o lento no altera ni retrasa la operación. Prohibido añadir tenant, owner, actor,
payload, prompt, ruta cruda o credenciales. El exportador OTLP por proceso sigue siendo de Trans04.

## 5. Replay durable — consumidores (trans02)

- Cursor: `sinceId` del último evento procesado. El store resuelve el cursor a su posición durable
  `(updated_at, id)`; un cursor ajeno o inexistente lanza `EVENT_CURSOR_NOT_FOUND`.
- Orden: `(updated_at, id)` ascendente, es decir, orden de inserción del log. `emittedAt` sigue siendo
  el tiempo declarado por el productor y puede ser anterior al cursor.
- Los consumidores deben deduplicar por `event.id` al reanudar y persistir el cursor **después** de
  procesar o descartar de forma auditable.
- Sin `select()` no hay paginación durable: `replayTenant` con filtros lanza `EVENT_REPLAY_UNSUPPORTED`.

## 6. `ACTION_DISPATCH_INTENT_V1` — recuperación postcommit

`actions` kind `action-dispatch`, `id = actionId`, `status: pending | settled | reconciled | orphaned`,
escrito en la misma transacción que el claim. `ActionService.reconcileDispatchIntents()` corre en
`maintain`: una intención pendiente cuya acción sigue `executing` pasa la acción a `outcome_unknown` con
`reconciliationRequired` y la intención a `reconciled`; nunca reenvía el efecto.
