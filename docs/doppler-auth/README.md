# Diagnóstico de despliegue y autenticación de AgntiaPro

La investigación se hizo sobre el remoto `uniscrolliabrain-cloud/agente`. El checkout local tenía cambios en curso y estaba por detrás de la rama remota. Para analizar el despliegue usé el workflow que GitHub sirvió para el commit de `v0.2.0-beta.3`, `3f15ca824af29ce15680c561fed3d7134c49b812`, y consulté los jobs de ambas betas. Las pruebas fueron de solo lectura. Se filtraron los logs y las respuestas para evitar imprimir valores secretos. No se modificaron credenciales, permisos ni despliegues. [Workflow de beta.3](https://github.com/uniscrolliabrain-cloud/agente/blob/3f15ca824af29ce15680c561fed3d7134c49b812/.github/workflows/deploy.yml)

## Ruta de las credenciales y discrepancias

- El `doppler.yaml` de la referencia local configura `agntiapro/dev`. El workflow de beta.3 usa el entorno GitHub `production` para el tag y toma `DOPPLER_CONFIG` de las variables de Actions, con `prd` como valor por defecto. GitHub confirmó que existe el entorno `production`, pero devolvió `403` cuando intenté listar nombres y fechas de secretos tanto del repositorio como de ese entorno.
- Actions lee `DOPPLER_TOKEN` y `FLY_API_TOKEN` desde sus secretos. Descarga la configuración Doppler, filtra credenciales de infraestructura y envía los valores restantes a Fly mediante `flyctl secrets import --stage`, primero a la API y después al worker. La descarga y la importación comparten el mismo paso. El log filtrado mostró errores de aplicación y autenticación, pero quedó sin aislar qué credencial originó el fallo de producción.
- El job de Vercel toma `VERCEL_TOKEN`, `VERCEL_ORG_ID` y `VERCEL_PROJECT_ID` de GitHub. La configuración Doppler consultada también contiene nombres de tokens de Vercel, Fly y Cloudflare. Renovar una copia no actualiza por sí solo la otra. El token rechazado por Vercel en beta.2 es el único que se confirmó inválido en la ejecución que lo usó. Quedó pendiente identificar qué copias están vigentes o duplicadas en producción y Freebuff.
- La configuración Doppler accesible contenía `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `TOKEN_ENCRYPTION_KEY` y `PUBLIC_API_URL`. Su `PUBLIC_API_URL` difería tanto del origen `.com` de producción como del `.io` documentado. Esa configuración es distinta de la configuración efectiva de producción, que queda por comprobar.

## Google OAuth, Gmail, Drive y Calendar

- El servidor deriva el callback de `PUBLIC_API_URL` y añade `/api/google/callback`. Fly declara `https://www.agntiapro.com/api/google/callback` y la guía de secretos indica `https://www.agntiapro.io/api/google/callback`. El host `.io` no resolvió durante la prueba. En `.com`, el endpoint de estado devolvió `401` sin sesión y el callback devolvió `400` sin código. Esto confirma que las rutas responden. Queda por comparar la URI que realmente emite el runtime con la registrada en el cliente OAuth. [Guía del repositorio](../operacion/SECRETOS.md) · [Requisitos de redirect URI de Google](https://developers.google.com/identity/protocols/oauth2/web-server)
- El flujo solicita PKCE, acceso offline y consentimiento. En lectura solicita `gmail.readonly`, `drive.readonly`, `calendar.events.readonly` y `calendar.calendarlist.readonly`. El modo escritura solicita scopes adicionales para los tres servicios. Estos son los scopes que pide el código. Los scopes concedidos para una cuenta real siguen sin verificar.
- El callback intercambia el código con Google y después consulta el perfil de Gmail. Si Gmail rechaza la consulta, el código no guarda la conexión, lo que también bloquea el acceso a Drive y Calendar. Esto es una dependencia confirmada en el código. Aún falta comprobar si explica el fallo observado por el usuario.
- El servidor guarda las credenciales del usuario cifradas y usa el refresh token al vencer el access token. Si Google no devuelve uno nuevo, el callback conserva el anterior solo cuando corresponde a la misma cuenta. Falta comprobar si existe un refresh token utilizable, si se puede descifrar con la clave del runtime y si Google lo acepta. También quedan por verificar las APIs habilitadas, la audiencia y el estado de publicación. Si la app es externa y está en modo Testing, Google documenta una vigencia de siete días para refresh tokens con estos tipos de scopes. [Expiración de refresh tokens](https://developers.google.com/identity/protocols/oauth2#expiration)

## Qué haría al retomar

1. **Separar Doppler y Fly en el diagnóstico.** Preparar una comprobación de solo lectura que use el entorno y las referencias de GitHub reales. Validar por separado que `DOPPLER_TOKEN` llega a la configuración esperada y que Fly reconoce cada app con el `FLY_API_TOKEN` efectivo. Reportar solo resultados y códigos. Proponer una corrección del workflow según el error aislado. La CLI de Doppler no estaba instalada en esta sesión. Usé su API para las comprobaciones disponibles. Instalaría la CLI oficial si hace falta reproducir el comportamiento exacto del runner. [Instalación de Doppler CLI](https://docs.doppler.com/docs/install-cli)
2. **Rastrear Freebuff.** Con acceso al job fallido, comparar su destino y sus referencias de credenciales con Actions. Comprobar si ejecuta el workflow por tag o despliega directamente y en qué punto rechaza el proveedor la operación. El conector de Vercel estaba disponible para instalación y seguía sin conectar al cierre.
3. **Probar Google con una cuenta de prueba.** Desde una sesión autorizada, comprobar el callback real y el resultado del intercambio OAuth. Validar con llamadas de lectura mínimas el perfil de Gmail, la lista de calendarios y el acceso a Drive. Comprobar el refresh por separado y reportar códigos de error y scopes concedidos, sin incluir tokens, respuestas privadas ni contenido de usuario. Si se confirma que Gmail impide conectar los otros servicios, proponer desacoplar esa validación según las necesidades del producto.
4. **Verificar la reparación.** Con aprobación para los cambios y el despliegue, repetir el flujo de release y comprobar que la API y el worker ejecutan el commit esperado, que el sitio apunta al proyecto correcto y que el smoke test se ejecuta. Repetir las comprobaciones de Google sobre ese runtime.
